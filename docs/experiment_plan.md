# План экспериментального исследования ACFSA

## 1. Цель и гипотеза

Цель — оценить, может ли адаптивная фильтрация и структурирование контекста сократить объём информации, передаваемой LLM, без ухудшения качества извлечения и итоговых ответов.

Гипотеза: сочетание устойчивого адаптивного порога релевантности и MMR-отбора уменьшает долю низкорелевантных и повторяющихся текстовых блоков по сравнению с top-K RAG.

## 2. Объект и предмет

Объект — поток контекстных фрагментов, возвращаемых RAG-поиском. Предмет — алгоритмы оценки соответствия фрагмента запросу, адаптивного отсечения и подавления семантической избыточности.

## 3. Данные

Рекомендуется сформировать корпус из 30–100 документов для пилота и расширить его для итогового исследования. Допустимые типы: внутренние инструкции, регламенты, технические документы и законно доступные нормативные тексты. Текст разбивается на одинаковые чанки (стартово 400–700 токенов, overlap 50–100 токенов). Формируется набор из 50–100 и более вопросов. Каждый вопрос размечается релевантными источниками/фрагментами и эталонным ответом. Желательны два независимых эксперта.

Запросы делятся на train/validation/test, например 60/20/20. Настройка параметров выполняется только на validation. Закрытые документы и чувствительные сведения не загружаются в публичный репозиторий.

## 4. Сравниваемые режимы

| Режим | Обработка | Назначение |
|---|---|---|
| Baseline | Retriever → top-K | Контроль |
| Adaptive only | Retriever → адаптивный порог → top-K | Вклад первого механизма |
| MMR only | Retriever → MMR | Вклад второго механизма |
| ACFSA | Retriever → порог → exact dedup → MMR | Полный алгоритм |

В основном сравнении должны совпадать корпус, chunking, embedding-модель, первичный top-N, LLM, системный prompt, температура и token budget.

## 5. Метрики

- Precision@K, Recall@K, MRR, nDCG@K — качество извлечения.
- `Compression = 1 - Tokens(ACFSA)/Tokens(Baseline)` — относительное сокращение контекста.
- Число чанков и уникальных источников; средняя попарная similarity выбранных чанков.
- Retrieval latency, время фильтрации и полное время ответа.
- При включённой LLM: экспертная оценка корректности, полноты, groundedness и неподтверждённых утверждений по рубрике 0–4; оценивание вслепую.

BLEU/ROUGE не следует использовать как единственное доказательство фактической корректности.

## 6. Протокол

1. Зафиксировать версии Python, библиотек, embedding-модели, LLM и commit hash.
2. Подготовить корпус и стабильные `doc_id`/`chunk_id`.
3. Разметить вопросы и разделить выборки.
4. Построить общий индекс; один Retriever используется во всех вариантах.
5. Для каждого тестового вопроса выполнить Baseline, Adaptive only, MMR only и ACFSA.
6. Сохранить retrieval scores, adaptive threshold, решения фильтра, MMR scores, token count и latency.
7. При включённой LLM получить ответы всех режимов по одному prompt; отправить ответы экспертам без указания метода.
8. Выполнить абляции и анализ чувствительности к параметрам.
9. Рассчитать агрегаты, доверительные интервалы и парные статистические тесты.

## 7. Статистический анализ

Для одинаковых запросов использовать попарные разности метрик. При подходящих предпосылках — paired t-test; иначе — Wilcoxon signed-rank test. Для нескольких сравнений применять коррекцию Holm. Приводить размер эффекта и 95%-й доверительный интервал, а не только p-value.

## 8. Выводы

Алгоритм считается перспективным, если сокращение контекста воспроизводимо, а Recall и качество ответов не ухудшаются недопустимым образом. Снижение токенов при существенном падении полноты — не положительный результат. Все проценты и графики в статье должны основываться только на фактически выполненных измерениях.
