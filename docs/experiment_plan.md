# План экспериментального исследования ACFSA

## 1. Цель и гипотезы

**Цель:** экспериментально установить, позволяет ли ACFSA уменьшить объём контекста, передаваемого LLM-агенту, при сохранении достаточной полноты извлечения и качества ответа.

**Исследовательский вопрос:** даёт ли сочетание адаптивного порога релевантности и MMR статистически подтверждаемое сокращение контекста по сравнению с top-K RAG без недопустимого ухудшения retrieval-метрик и ответов?

Проверяемые гипотезы:

- **H1 — сжатие:** ACFSA уменьшает число токенов контекста по сравнению с baseline.
- **H2 — снижение избыточности:** ACFSA снижает среднюю попарную семантическую близость выбранных фрагментов.
- **H3 — сохранение полноты:** Recall@K и nDCG@K не ухудшаются более чем на заранее заданную границу.
- **H4 — качество ответов:** экспертная оценка фактической корректности, полноты и обоснованности источниками не хуже baseline.

Гипотезы не являются результатами. Проценты улучшения нельзя указывать до выполнения эксперимента.

## 2. Объект, предмет и переменные

- **Объект:** контекстные фрагменты, найденные RAG-системой в документальном корпусе.
- **Предмет:** оценка релевантности, адаптивное отсечение, подавление семантической избыточности и формирование компактного контекста.
- **Независимая переменная:** метод формирования контекста (Baseline, Adaptive only, MMR only, ACFSA).
- **Зависимые переменные:** Precision@K, Recall@K, MRR, nDCG@K, число токенов, compression ratio, средняя попарная similarity, число выбранных чанков, задержка, экспертная оценка ответа.
- **Контролируемые переменные:** корпус, chunking, overlap, embeddings, Retriever, top-N, LLM, prompt, temperature и максимальная длина ответа.

## 3. Методы сравнения

| Метод | Конвейер | Назначение |
|---|---|---|
| Baseline | Retriever → top-K | Контроль |
| Adaptive only | Retriever → порог → top-K | Вклад механизма релевантности |
| MMR only | Retriever → точная дедупликация → MMR | Вклад подавления избыточности |
| ACFSA | Retriever → порог → дедупликация → MMR | Совместный эффект |

Все методы должны получать один и тот же ранжированный список top-N от одного Retriever. Абляции необходимы, чтобы измерить вклад каждого механизма отдельно.

## 4. Данные и разметка

### 4.1. Документальный корпус

Для пилота можно начать с 30–100 документов; итоговый корпус желательно расширить. Подходят инструкции, регламенты, технические документы и открытые нормативные материалы. Для каждого документа фиксируются `doc_id`, источник, название, редакция, дата и статус действия.

### 4.2. Сегментация

Стартовый ориентир — 400–700 токенов на фрагмент и overlap 50–100 токенов. По возможности границы чанков совмещаются с абзацами, пунктами и подпунктами. Один и тот же набор чанков используется всеми методами. В текущем прототипе репозитория используется char-based segmentation через `max_chars` и `overlap_chars`; перед полномасштабной статьёй следует либо перейти на tokenizer-aware разбиение, либо зафиксировать текущую схему без изменений и описать её как ограничение.

### 4.3. Вопросы и эталонная разметка

Для пилота достаточно тестовых вопросов репозитория. Для итогового исследования желательно не менее 50–100 разнообразных запросов, при наличии ресурсов — 200 и более. На каждый вопрос указываются релевантные `doc_id` или `chunk_id`, reference answer и список ключевых фактов.

Рекомендуемые типы: фактологические, процедурные, многодокументные, уточняющие, с недостаточным подтверждением и с конфликтующими редакциями документов. Желательна независимая разметка двумя экспертами с последующим согласованием.

Разделение вопросов: train/validation/test, например 60/20/20. Параметры ACFSA настраиваются только на validation. Test используется один раз для итоговой оценки.

## 5. Реализация алгоритма

### Механизм 1: релевантность

1. Закодировать запрос и фрагменты моделью embedding.
2. Вычислить `s_i = cosine(E(Q), E(d_i))`.
3. Рассчитать `m = median(S)`, `MAD = median(|s_i-m|)`, `sigma_r = 1.4826*MAD`.
4. Рассчитать `T(Q) = max(T_min, m - beta*sigma_r)`.
5. Оставить фрагменты, для которых `s_i >= T(Q)`.
6. Если ни один кандидат не прошёл порог, вернуть пустой контекст, а не форсировать слабый результат.

Медиана и MAD уменьшают влияние одиночных экстремальных score. `T_min` — абсолютная нижняя граница; `beta` управляет мягкостью фильтра. Это эвристический query-specific порог, а не вероятность релевантности.

### Механизм 2: избыточность

1. Удалить точные дубликаты нормализованных строк, оставив экземпляр с максимальной релевантностью.
2. Для кандидатов рассчитать межфрагментную cosine similarity.
3. Жадно максимизировать `MMR(d_i) = lambda*RelNorm(d_i,Q) - (1-lambda)*maxSim(d_i,A)`.
4. Повторять выбор до достижения `K` или исчерпания кандидатов.

`lambda=1` выключает штраф за повторение, `lambda=0` делает приоритетом разнообразие после первого выбора. Промежуточное значение балансирует обе составляющие. Выбранный контекст упаковывается с сохранением source/doc_id/chunk_id и версии документа.

## 6. Метрики

### 6.1. Retrieval

- Precision@K;
- Recall@K;
- MRR;
- nDCG@K.

Если разметка задана на уровне `doc_id`, метрики должны рассчитываться по уникальным документам: несколько чанков одного документа не могут считаться несколькими независимыми находками. Дополнительно можно считать chunk-level метрики при наличии разметки `chunk_id`.

### 6.2. Сжатие и избыточность

\[
Compression = 1 - \frac{Tokens(ACFSA)}{Tokens(Baseline)}.
\]

Число токенов считается совместимым tokenizer для используемой LLM. Дополнительно фиксируются число чанков, число уникальных источников и средняя попарная cosine similarity выбранных блоков. Пустой контекст помечается отдельно: он не доказывает успешное сжатие без потери качества.

### 6.3. Время

Отдельно регистрируются retrieval latency, filtering/MMR latency, LLM latency и end-to-end latency. Сравниваются медиана и разброс.

### 6.4. Качество LLM-ответа

При включённой генерации ответы всех режимов строятся одной LLM с одинаковыми настройками. Два эксперта вслепую оценивают:

- фактическую корректность (0–4);
- полноту (0–4);
- обоснованность источниками (0–4);
- отсутствие неподтверждённых утверждений (0–4, где 4 — неподтверждённых утверждений нет).

BLEU/ROUGE не используются как единственное доказательство фактической корректности. Желательно рассчитать межэкспертную согласованность, например взвешенную κ Коэна.

## 7. Протокол выполнения

1. Зафиксировать commit hash, Python, версии библиотек, embedding-модель и её ревизию, Retriever и LLM.
2. Подготовить корпус, очистить дубликаты версий и назначить стабильные `doc_id` и `chunk_id`.
3. Разбить документы на чанки один раз, зафиксировать параметры сегментации.
4. Подготовить вопросы, эталонные ответы, ключевые факты и разметку релевантности.
5. Разделить вопросы на train/validation/test.
6. Построить единый embedding-индекс; один Retriever и top-N использовать для всех режимов.
7. На validation подобрать `T_min`, `beta`, `lambda`, `top-N` и `K`; зафиксировать значения.
8. Для каждого test-вопроса выполнить Baseline, Adaptive only, MMR only и ACFSA.
9. Сохранить исходные score, адаптивные пороги, отсеянные и выбранные `chunk_id`, MMR-score, токены и время этапов.
10. При включённом LLM сформировать ответы одним prompt и одинаковыми параметрами.
11. Провести слепую экспертную оценку ответов.
12. Рассчитать метрики, доверительные интервалы, парные тесты и анализ ошибок.
13. Подготовить таблицы и графики только из фактических outputs; зафиксировать commit hash и конфигурацию.

## 8. Настройка параметров

Стартовая сетка для validation (уточняется под корпус и модель):

| Параметр | Варианты |
|---|---|
| top-N | 20, 30, 50 |
| K | 3, 5, 8, 10 |
| T_min | 0.50, 0.55, 0.60, 0.65, 0.70 |
| beta | 0.5, 1.0, 1.5, 2.0 |
| lambda | 0.50, 0.60, 0.70, 0.80, 0.90 |

Параметры выбираются по validation с ограничением на полноту и качество ответов, а не только по минимуму токенов.

## 9. Статистическая обработка

- Все методы сравниваются на одних и тех же test-вопросах; единица анализа — запрос.
- Для метрик приводятся среднее, медиана, стандартное отклонение и 95%-й доверительный интервал.
- Для парных различий применяется paired t-test при обоснованных предпосылках; иначе Wilcoxon signed-rank test.
- Дополнительно рекомендуется парный bootstrap по вопросам (например, 10 000 повторов) для доверительного интервала разности и compression ratio.
- Для множественных парных сравнений применяется коррекция Holm.
- Указываются размер эффекта и практическая значимость, а не только p-value.
- При малой выборке результаты обозначаются как пилотные.

## 10. Артефакты эксперимента

Результаты текущего runner сохраняются в `outputs/latest/`:

- `results_per_query.csv` — метрики по каждому запросу и методу;
- `summary.csv` — сводная статистика;
- `audit.json` — retrieval scores, threshold, выбранные чанки;
- `run_metadata.json` — конфигурация запуска и сведения о моделях;
- `tokens_comparison.png`, `recall_comparison.png`, `ndcg_comparison.png`, `latency_comparison.png` — графики;
- `answers_for_blind_review.csv` — ответы LLM и поля экспертной оценки, если генерация включена.

## 11. Интерпретация и ограничения

Положительный результат — воспроизводимое уменьшение контекста при сохранении Recall и фактического качества ответа в заранее заданной допустимой границе. Снижение токенов при существенном падении полноты или росте неподтверждённых утверждений не является улучшением.

Embedding similarity не проверяет истинность, свежесть или нормативную применимость. MMR может ошибочно считать повторяющимися тематически близкие, но юридически разные пункты. Для критичных документов нужно сохранять версии и даты действия, а также проводить экспертную проверку.

Текущий демонстрационный корпус репозитория состоит из пяти синтетических документов и семи вопросов. Он предназначен для smoke test и проверки воспроизводимости конвейера, но не для вывода о научной эффективности.
